# D2-04.1 — LibreOffice Basic UNO Harness

## Status

**DESIGN APPROVED — implementation plan pending**

## Context

D2-04.0 established and validated the LibreOffice 7.4.7.2 runtime baseline in GitHub Actions. D2-04.1 adds the first real execution bridge between CI and CompareFramework Basic code.

The runtime baseline remains exactly LibreOffice **7.4.7.2**. Other LibreOffice versions are outside the scope of this delivery.

CompareFramework is delivered to users as a generated monolithic `.bas` file. D2-04.1 therefore validates the real delivery chain rather than bypassing packaging by loading individual `src/*.bas` modules.

## Goal

Prove on a fresh GitHub Actions runner that the monolith generated by `tools/build_monolith.py` can be loaded into a real `.ods` document under LibreOffice 7.4.7.2, invoked as LibreOffice Basic, and produce a deterministic result that the CI harness can verify without user interaction.

The contractual execution path is:

`src/*.bas -> tools/build_monolith.py -> dist/*.bas -> CI fixture .ods -> UNO injection -> CF_CI_RuntimeSmoke -> CompareFramework_CI sheet -> UNO result read -> PASS/FAIL`

## Non-goals

D2-04.1 does not:

- execute the T001–T010 business regression scenarios;
- execute a full comparison;
- invoke `CF_RunReleaseValidation`;
- change the six supported user-facing API procedures frozen by D2-03.24;
- introduce support for LibreOffice versions other than 7.4.7.2;
- replace the monolith with direct loading of `src/*.bas`;
- introduce Docker or a separate packaging format.

Business scenario automation belongs to D2-04.2.

## Architecture

### 1. Monolith as the tested artifact

The harness must run `tools/build_monolith.py` first and use the resulting monolithic `.bas` artifact from `dist/`.

The harness must never reconstruct CompareFramework from individual source modules. This ensures that D2-04.1 validates the same packaging boundary used by real users:

- source parsing and assembly;
- monolith generation;
- LibreOffice Basic loading;
- runtime invocation.

A successful test against stale or embedded Basic code is not acceptable evidence.

### 2. Versioned `.ods` CI fixture

Add a minimal `.ods` fixture under a dedicated CI fixture directory, expected to be:

`tests/fixtures/ci/CompareFramework_CI.ods`

The fixture is a real LibreOffice Calc document but does not contain a frozen copy of the CompareFramework monolith. The harness always injects the freshly generated monolith at runtime.

The fixture contains or permits creation of the technical result sheet named exactly:

`CompareFramework_CI`

The fixture exists to provide a stable real-document container for Basic execution and to become the foundation for later D2-04.2 scenarios.

### 3. Python/UNO orchestrator

Add a repository-owned Python harness, expected to be:

`tools/ci/run_libreoffice_basic_smoke.py`

Its responsibilities are limited and explicit:

1. locate the generated monolith;
2. copy the versioned fixture into a temporary work directory;
3. start or connect to LibreOffice 7.4.7.2 running headlessly with an isolated temporary user profile;
4. open the temporary `.ods` through UNO;
5. inject the monolith into a document Basic library/module;
6. resolve and invoke `CF_CI_RuntimeSmoke`;
7. read the deterministic result from the `CompareFramework_CI` sheet;
8. validate the result contract;
9. close the document and LibreOffice cleanly;
10. return a non-zero exit code for every failed stage.

The harness must not depend on a user's LibreOffice profile, GUI state, desktop session, or interactive security prompt.

### 4. Technical Basic smoke entrypoint

Add a technical procedure named exactly:

`CF_CI_RuntimeSmoke`

This procedure is part of the runtime test contract but **not** part of the six supported user APIs frozen by D2-03.24.

It must be non-interactive and deterministic. It must not open dialogs, run a comparison, invoke release validation, or depend on workbook-specific business data.

Its sole purpose is to prove that the freshly generated CompareFramework monolith has been loaded and that executable Basic code can modify the active CI document.

The result contract is:

- sheet: `CompareFramework_CI`
- `A1 = STATUS`
- `B1 = OK`
- `A2 = MARKER`
- `B2 = COMPAREFRAMEWORK_CI_SMOKE_OK`

The harness declares success only when `B1` and `B2` match the expected values exactly.

### 5. Public API freeze compatibility

`CF_CI_RuntimeSmoke` must not be added to `CompareFramework_API.bas` and must not alter the canonical six-procedure supported user API contract.

It may remain `Public` if LibreOffice Basic runtime invocation requires that visibility, but architecture/audit logic must classify it as a technical CI entrypoint outside the supported user-facing API.

D2-03.24 regression tests must remain green.

## Runtime flow

The GitHub Actions job executes the following sequence:

1. check out the repository;
2. establish LibreOffice 7.4.7.2 using the validated D2-04.0 installer;
3. build the current monolith with `tools/build_monolith.py`;
4. run static D2-04.1 contract tests;
5. start LibreOffice headlessly using a unique temporary profile and a bounded timeout;
6. establish an UNO connection;
7. open a temporary copy of `CompareFramework_CI.ods`;
8. inject the freshly built monolith;
9. invoke `CF_CI_RuntimeSmoke`;
10. verify the `STATUS` and `MARKER` cells via UNO;
11. close the document and terminate the LibreOffice process cleanly.

No successful LibreOffice process exit is sufficient by itself. The result cells are mandatory proof of successful Basic execution.

## Error handling

D2-04.1 uses fail-fast semantics with stage-specific diagnostics.

Hard failures include:

- unexpected LibreOffice version;
- monolith build failure;
- generated monolith missing or empty;
- fixture missing or invalid;
- LibreOffice startup timeout;
- UNO connection timeout;
- document open failure;
- Basic library/module injection failure;
- `CF_CI_RuntimeSmoke` missing or not resolvable;
- macro invocation failure;
- result sheet missing;
- `STATUS` not equal to `OK`;
- marker not equal to `COMPAREFRAMEWORK_CI_SMOKE_OK`;
- unrecoverable document/process shutdown failure.

The harness must distinguish infrastructure failures from CompareFramework execution failures in its messages where practical.

Cleanup is mandatory through `try/finally`-style control flow or equivalent. The harness always attempts document close, UNO cleanup, process termination, and removal of temporary files/profile even after a failed test stage.

A global timeout prevents an invisible dialog, stalled macro, or broken UNO connection from consuming the CI runner indefinitely.

## Testing strategy

### 1. Static contract tests

Repository tests verify at minimum:

- the D2-04.1 fixture exists;
- the harness identifies the `CompareFramework_CI` sheet contract;
- the harness expects `STATUS=OK`;
- the harness expects `COMPAREFRAMEWORK_CI_SMOKE_OK`;
- the generated monolith contains `CF_CI_RuntimeSmoke`;
- the harness consumes a built artifact from `dist/` rather than `src/*.bas` directly;
- D2-04.1 does not invoke T001–T010, a business comparison, or `CF_RunReleaseValidation`;
- the six supported user APIs remain unchanged.

Static tests are necessary but are not sufficient for validation.

### 2. Real integration test

The dedicated GitHub Actions runtime test must prove all of the following on LibreOffice 7.4.7.2:

- the current monolith builds successfully;
- the fixture opens via UNO;
- dynamic Basic injection succeeds;
- `CF_CI_RuntimeSmoke` resolves and executes;
- `CompareFramework_CI!B1` equals exactly `OK`;
- `CompareFramework_CI!B2` equals exactly `COMPAREFRAMEWORK_CI_SMOKE_OK`;
- the document and LibreOffice process terminate cleanly.

### 3. Negative-path proof

D2-04.1 includes two narrowly scoped negative validations:

1. invoking a deliberately nonexistent Basic procedure must fail with a macro-resolution/invocation diagnostic and non-zero harness status;
2. validating against a deliberately incorrect expected marker must fail at the result-validation stage.

These checks prove that the harness is detecting execution/result failures rather than merely observing that LibreOffice exited.

## Relationship with existing CI

The validated D2-04.0 runtime baseline remains the source of the LibreOffice 7.4.7.2 installation mechanism.

The D2-03.24 cumulative architecture/regression workflow remains green and retains its existing responsibility.

D2-04.1 may extend or introduce a dedicated runtime workflow, but must preserve clear failure attribution between:

- architecture/build regressions;
- LibreOffice runtime establishment;
- UNO harness failures;
- Basic injection/invocation failures;
- result-contract failures.

## Security and macro execution

The CI environment is ephemeral and uses an isolated temporary LibreOffice profile.

The harness loads only repository-owned fixture and Basic content generated from the checked-out repository. It must not weaken macro security globally on a persistent user profile.

If LibreOffice macro security prevents programmatic execution, the implementation must solve this only inside the isolated CI profile or through the UNO invocation mechanism; it must not require manual approval or persistent system-wide configuration.

## Expected deliverables

D2-04.1 is expected to produce:

- `tools/ci/run_libreoffice_basic_smoke.py`;
- `tests/fixtures/ci/CompareFramework_CI.ods`;
- a technical Basic source containing `CF_CI_RuntimeSmoke` and included in the generated monolith;
- static D2-04.1 contract tests;
- CI integration for the real UNO/Basic smoke test;
- `D2_04_1_REPORT.md` containing the final runtime evidence.

Exact supporting filenames may be refined in the implementation plan while preserving these responsibilities and contracts.

## Validation criteria

D2-04.1 is complete only when all of the following are true:

1. LibreOffice is exactly version 7.4.7.2.
2. `tools/build_monolith.py` produces the artifact actually injected into the fixture.
3. The versioned `.ods` fixture is opened in an isolated-profile headless LibreOffice process.
4. The monolith is dynamically injected through UNO.
5. `CF_CI_RuntimeSmoke` is found and executed as real LibreOffice Basic code.
6. `CompareFramework_CI!B1` is exactly `OK`.
7. `CompareFramework_CI!B2` is exactly `COMPAREFRAMEWORK_CI_SMOKE_OK`.
8. Document and process shutdown completes without blocking.
9. Static contract tests pass.
10. Both negative-path tests fail for their expected reasons.
11. D2-03.24 cumulative validation remains green.
12. A fresh GitHub Actions run on the final PR HEAD completes with `success`.

`D2_04_1_REPORT.md` remains `IMPLEMENTED — verification pending` until that final fresh runtime evidence exists. Only then may its status become **VALIDATED**.
